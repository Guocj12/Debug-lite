## 1. 绘制范围（用户给定边界，不可协商）

1.1 本轮设计**只考虑前后端交互**与**按钮功能的完整性**；不考虑样式、动画、布局与视觉呈现。
1.2 绘制手段**封闭**为基本控件：**按钮、文字、输入框**（及其同类基本控件）。除此之外不引入任何图形绘制。
1.3 任何「本该画出来」的运行时内容（元素移动、命中、状态变化等动画语义）**一律转为文字表述**，
    例如 `元素p1：位置224`。不得引入画布、图形、精灵或动画。
1.4 文本化产物必须**自足**：把结果直接交给绘制方法即可绘制；
    **绘制方法内不得再查状态、再算公式、再拼字符串**（「绘制方法零逻辑」）。
1.5 由 §1.2–§1.4 直接推出的两条硬规则（违反即视为设计不完整）：
    - **投影单一真源**：后端数据 → 文字描述 的转换只能有一处实现，禁止前端与其他调用方（如 CLI）各写一份。
    - **禁止前端复制战斗公式**：伤害 / 命中 / 移动 / 胜负一律消费服务端结果，前端只做展示。

## 2. 协作协议（「反驳式提问」= **AI 攻击用户的提案**）

> 方向定义（用户 2026-09-20 澄清，最高优先）：用户给出一部分设计后，我的第一动作是**反驳它**——找出其中不合适的、
> 与既有约束冲突的、缺失败路径的、判据不可判定的、以及用户未意识到的副作用与代价。
> **「我给出 A/B 选项请你挑一个」不算反驳**，也不构成任何定稿依据。

2.1 **先查后驳**：反驳前先按权威链检索既有结论。能查到答案的**不作为问题提出**，直接作为反驳依据（附 `文件:行号`）。
    查到设计与上游冲突 → 立即停止，把冲突作为**第一号反驳**。
2.2 **射程**：只反驳当前这部分设计；**不得以「更合理」为名侵蚀上游权威**（`docs/decisions.md` / `docs/interfaces.md` /
    `server/core` 战斗语义）。命中上游 → 走 §2.7 升级，不得自行绕过，也不得用「前端兜底」消化。
2.3 **证据等级**：设计意图可引文档；**运行时可观测事实（字段 / 错误码 / 状态码 / 可达性 / 性能量级）必须实测**
    （真实 HTTP 或进程内起服务断言），**只引文档不算证据**。
2.4 **每条反驳的规格**：编号 + 主张 + **反例或后果**（按你的设计实现，具体会在哪里坏、怎么坏）+ 备选与代价 + 证据。
    **提不出具体反例的「我觉得不好」不得提出。**
2.5 **盲区声明**：每轮必须显式给出「我这轮可能错在哪」（未验证的假设、未覆盖的情形、我依赖的二手结论）。
    **「本轮无可反驳」不得单独出现**，必须与盲区声明同时给出。
2.6 **升级路径**：同一议题 3 轮未收敛 → 我给出二选一 + 各自代价 → 用户拍板 → 记入 §5；
    涉及上游契约则走 D 编号（§2.7）。
2.7 **后端契约不可前端私改**：凡需改动 `/api/v1` 的路径、字段、错误码、鉴权的诉求，
    一律升级为决策记录（`docs/decisions.md` 追加 D 编号）+ 同步 `docs/interfaces.md`，
    走 `docs/tasks.md` §10 变更流程。
2.8 **顺从性防线**：用户对我的反驳回「同意 / 可以」时，我必须复述「你同意的是哪一条、是否接受我列的副作用」，
    得到明确回复才算确认；**不得把模糊同意当成定稿**。
2.9 **产出物**：每轮结束必须产出 ① 反驳清单（逐条：采纳 / 驳回 / 待定 + 理由）② §5 FR 增量 ③ §6 开放项增量 ④ 盲区声明。
    **驳回我的反驳也必须写明理由**（否则下一轮我会重复提，或你被迫重复解释）。
2.10 **定稿判定（四项全过）**：① 与行业主流做法的关系已说明（点名模式 + 被否决替代 + 本项目**采/不采**的理由；
    **主流只作对照，不作合格线**——本项目刻意反主流：零依赖 / 无框架 / 单进程）；② 既有约束下合理（无权威链冲突、无门禁冲突）；
    ③ 功能完整（**全部用户动作 + 全部失败路径**）；④ 已明确到可逐行实现（字段名、边界条件、错误分支无待定项）。
    **附加**：③ 必须附「已知未覆盖 / 已知风险」清单（不得为空）；判定结论**只能由 `docs/reviews/F<n>.md`（独立上下文）出具**，
    分册正文不得自署「四项全过」。
2.11 **不批量默认同意**：用户一次给出多屏 / 多流程时，按单元分批处理，**一批一轮**。

## 3. 文档体系与机器纪律

3.1 **位置与命名**：总纲 = `docs/frontend/00-rules.md`；后续分册 = `docs/frontend/<两位序号>-<主题>.md`。
3.2 **批次命名**：P6 批次必须**避开** `P\d+-\d+` 与 `B\d+` 两种形态——
    `scripts/check-docs.js` 的批次行正则会把它们并入「批次计数」，与现状「共 41 批」直接冲突（check-docs FAIL）。
    最终命名形态与其审查记录要求见开放项 O-6。
3.3 **引用即承诺**：本目录文档若出现 npm 脚本引用、或引用 `scripts/`、`assets/`、`server/data/` 下的具体文件，
    即构成「该文件存在」的承诺（对应 check-docs 的 D1/D2/D3 检查）；尚未落地的一律显式标注「计划中 / 未实现」。
3.4 **文档不得与实现漂移**：任何设计改动须在**同一提交**内更新相应分册与 `docs/progress.md`。

## 4. 验收机制（只规定「必须存在什么」，不规定技术做法）

> 背景：前两轮前端「机器测试全绿但不可玩」（见 `docs/acceptance.md` §8）。以下为**防复发条款**。

4.1 **按钮永不无声**：每个可点元素必须命中一个已实现的动作分支；必须存在**机器可判定**的全覆盖检查
    （既不存在「注册了但没实现」，也不存在「实现了但无入口」）。
4.2 **字段名不得来自散文**：前端读取的每个响应字段必须可追溯到**真实 HTTP 响应**；
    必须存在**机器可判定**的「文档 ↔ 真实响应」核对手段。
4.3 **端点可达**：`docs/interfaces.md` §2 的每个端点必须有明确 UI 路径，或被显式登记为「本轮不做」。
4.4 **可玩性出口**：每批必须能在真实浏览器按「人工走查剧本」（点哪里 / 看什么 / 期望文本）走完该批流程；
    只有机器断言不算完成。每批的实际走查结论写入 `docs/reviews/`。
