### P2 登记（不阻塞，建议当批或 B16 处理）

1. **P2-1（文档同步）** `docs/interfaces.md:32` §1 ai/runtime 行与 `docs/systems/08-ai.md:109` §6 对外接口均未登记新增导出 `TRACE_LIMIT` / `RECURSION_LIMIT`（§1 行仍止于 STEP_LIMIT；`getVar` 亦缺，属 B14 前遗留）；B15 已交付"三大常量一并导出"的实现，接口权威文档必须跟上。修复：两处各加 `TRACE_LIMIT / RECURSION_LIMIT`（顺手补 getVar）。
2. **P2-2（语义歧义，建议 B16 定稿）** trace 上限实现为「**总量 2000 冻结**」：`traceNode` 仅当 `ctx.trace.length < ctx.traceLimit` 才 push（runtime.js:131），长局累计微步超 2000 后（实测 3000 tick 的普通程序：trace 恒为 seq 0..1999 的最早 2000 条、traceTruncated=true）后续执行不再有 trace——与 systems §4.3.4「**单 tick** 上限 2000 条」（systems/08-ai.md:62）措辞存在歧义；A-9e「截断，后续不再记录」字面与实现一致，但「供前端高亮与排查」的长局价值受损（前端只能看到最早 2000 步）。建议明确：每 tick 上限 + 环形淘汰（保留最近 2000）或总量冻结择一写入文档；B16 serializeContext/回放落地前定稿。
3. **P2-3（可观测性）** A-9d catch 仅记 `message`（runtime.js:149），实现 bug 被静默成 wait 时无 stack 可查——建议 `data` 补 `e.stack`（或完整 err）。另建议注释/文档澄清真实抛错点：getter 注入在 `deepFreeze` 深度冻结读值处（runtime.js:26-31/154）即触发，而非 evalExpr getPath 求值时（实测 trace==[] 佐证）；行为契约不变。**若快照长期带毒（引擎 bug），每 tick 重复 ai.error+wait，无退避**——引擎侧 D-107 投影为受信输入，属理论路径，登记观察即可。
4. **P2-4（实现取向判定 + 文档补字）** A-9b「弹栈并继续」被实现为「重置入口（frames=[]）+ 立即 return wait，vars 保留、下一 tick 从入口继续」。判定**合规**：若改为「弹调用栈后当 tick 继续」，非终止递归会当 tick 重入 → 反复命中深度兜底直至步数兜底，整 tick 退化为 stepLimited（死循环风险）；B15 的立即 return 是唯一能同时保住 depthLimited 语义与「下一 tick 正常继续」的取法，且与 D-81/A-9a 的重置语义同类。残余差异：被丢弃帧中**部分消耗的 count 循环 remaining 丢失**（重置后循环从头重启）——vars 保留故可继续推进，边缘可观测差异。建议 examples/08-ai.md A-9b/A-5 两行（第 139/92 行）补「重置到程序入口」消歧。
5. **P2-5（B14↔B15 语义修订登记，已消解）** B14 审查（B14.md:22/36）记录 c1/c4/c5「guard 耗尽但 stepCount<limit（重入帧不计步）→ stepLimited undefined」；B15 统一为「guard 耗尽即 wait + 重置入口 + ai.step.limit(warn) + stepLimited=true」（runtime.test.js:328/363/371，runtime.js:272-277）。**判定：修订合规**——B14 该路径实测返回 wait 但**不重置、不记 warn、不置标记**，本身即 D-81「重置到入口+日志」的语义缺口（每 tick 循环重入空转）；B15 统一兜底属修正而非退化，测试同步修为 true 且加强（RT-16b c4 仍断言变量保留）。warn.steps 语义 = 实际推进步数（c1 例 steps=25<50），与 A-9a 规范场景 {steps:10000}（pBurnSteps 精确命中）不冲突。
