### F7-A（P1）封禁/解封不失效榜单排序缓存 ⇒ 被封禁玩家仍出现在两张榜上（违反 §8.6「封禁账号一律不进榜」）

- **位置**：`server/store/index-file.js:103-111`（`upsert` 的缓存失效条件）＋ `:199`（`board()` 在切片前才过滤 `!e.banned`）＋ `:142-150`/`:154-167`（两张榜的懒排序缓存）
- **主张**：榜的**行集**由 `banned` 决定（`:199` 的 `all = source.filter((e) => !e.banned && …)`），但 `upsert` 只在 `points/peakPoints/nickname/tier`（`sorted`）与 `tier/tierUpdatedAt/publicId`（`arrivalSorted`）变化时把缓存置 `null`；`banned` **不在任何一个集合里**。于是"封禁/解封"这一**不改排序键**的变更，会让**已经构建过的**缓存数组继续含旧行 ⇒ 榜上出现已被封禁的账号，直到下一次有人改段位/积分/昵称才自愈。
- **反例/复现**（真实 HTTP，`probe-f7-http-ban.js`，`DL_ADMIN_TOKEN` + `POST /api/v1/admin/ban`）：
  ```
  预热 arrival = 1:u_365fae64:mythic , 2:u_416d9f9f:epic , 3:u_9004036e:rare
  预热 points  = 1:u_365fae64 , 2:u_416d9f9f , 3:u_9004036e
  封禁榜首后 arrival 榜 = 1:u_365fae64 , 2:u_416d9f9f , 3:u_9004036e  total=3   ← 被封禁者仍在
  封禁榜首后 points  榜 = 1:u_365fae64 , 2:u_416d9f9f , 3:u_9004036e  total=3   ← 被封禁者仍在
  self（被封禁者本人带 Bearer 自查）= null                                   ← 同一响应内自相矛盾
  再改他人段位 → arrival = u_9004036e,u_416d9f9f                            ← 缓存一旦失效即自愈
  ```
  进程内探针同样复现（C1/C1b），且证明与"是否经 HTTP"无关：`sC.index.board({order:'points'})` 在 `setBanned` 之后仍返回旧行。**注意**：`tests/api/api-leaderboard.test.js` LB-1…LB-7 **没有一条**覆盖"封禁后榜单"（全文无 `banned`/`ban` 字样），故机器核对全绿掩盖了它。
- **严重度**：**P1**。① 违反 `docs/systems/11-account-store.md:790` 的明文契约；② 用户可见（管理端刚封禁的人仍在榜上、且**能从榜上点进去看其 publicId/nickname**）；③ 同族不同步还导致 `data.self`（`:205-215` 用新鲜数组算）与 `rows`（陈旧数组切片）**在同一响应里互相矛盾**（本人已封禁 → `self=null`，但 `rows` 里还列着他）。
- **处置建议**（精确到行，已用探针验证有效）：
  1. `index-file.js:103-106` 的 `sorted` 失效条件追加 `|| prev.banned !== entry.banned`；
  2. `index-file.js:108-109` 的 `arrivalSorted` 失效条件追加 `|| prev.banned !== entry.banned`；
  3. **更稳的写法**（推荐，避免以后再漏键）：把"影响 `board()` 输出的键"集中成一个数组（`BOARD_ROW_KEYS = ['publicId','nickname','points','tier','tierUpdatedAt','banned']`），`upsert` 里遍历比较一次，任一变化即同时置 `sorted = null; arrivalSorted = null;`。
  4. **回归**：`tests/api/api-leaderboard.test.js` 追加 **LB-8**：造 2–3 账号 → `GET ?limit=100` 预热 → `POST /admin/ban` 封禁榜首 → 立刻 `GET`（**不改任何排序键**）断言两榜 `rows` 与 `total` 都不含被封禁者、且 `self=null` 一致；再 `unban` 断言行回到榜上。

### F7-B（P1）迁移探针把"档案本身缺 `progress.tierUpdatedAt`"当成"索引缺字段" ⇒ 每次开机全量重建索引，且排序永不修正

- **位置**：`server/store/index-file.js:225-231`（`needsTierStamp`：`!Number.isInteger(entry.tierUpdatedAt)` 即判真）＋ `:26`（`entryOf`：档案缺该字段 → 索引条目录 `null`）＋ `server/store/adapter-json.js:999-1004`（`open()` 命中即 `rebuildIndexFromArchives(readAllArchivesForIndex())`）
- **主张**：迁移判据用了**条目值**（`null` 也判真），而不是"**键是否存在**"。重建从档案取值，若**档案本身**没有 `progress.tierUpdatedAt`（早期落档形态 / 外部改动 / 半写恢复后的档案），`entryOf` 仍写 `null` ⇒ 重建完成后 `needsTierStamp()` 依旧 `true` ⇒ **下一次开机再全量重建**。D-171⑤ 与 `docs/systems/11:463` 都声明这是**一次性**迁移（"此后正常路径不再触发"），实测**永不收敛**。
- **反例/复现**（`probe-f7-review.js` D4/D4b）：造 1 个账号 → 关服 → 手工删掉**档案**（`data/players/<aa>/<pid>.json`）里的 `progress.tierUpdatedAt`，同时删掉索引条目里的同名字段（模拟 pre-D-171 形状）→ 同 dataDir 重启两次：
  ```
  D4  FAIL 重建后索引值 = null，needsTierStamp=true，迁移日志=1   ← 补不上，判据仍真
  D4b FAIL 第三次开机迁移日志条数 = 1                            ← 每次开机都重建（不收敛）
  D3  PASS（对照组：档案字段完好时，第二次开机迁移日志 = 0）        ← 证明"索引缺键"路径本身是对的
  ```
  每次重建的代价 = 把 `players/` 全量读一遍（**每个档案一次磁盘读 + 反序列化 + 不变量断言**）＋ `flushIndexNow()` 立即原子重写 `index.json`；账号量越大越贵。**同时排序仍然错的**：`null` 在 `ensureArrivalSorted`（`:161-162`）里被映射成 `Number.MAX_SAFE_INTEGER`，即使该玩家在段位内**先到**，也会被排到本段位**末尾**（B4 实测落位 = `[50] → [100] → [null] → [缺字段]`）——与 `docs/systems/11:783` 的"缺失（老数据）时排在本段位末尾"字面一致，但**与该迁移存在的目的（段位榜按真实到达时间排序）相反**：迁移没有、也无法修正这一条。
- **严重度**：**P1**（运维级 + 声明未兑现）。不崩、不丢数据（索引是派生数据），但：① 违反 D-171⑤ 的"一次性"与"此后正常路径不再触发"；② 每次开机多一次全目录扫描 + 一次索引全量重写；③ 日志持续误导（每次都记"索引缺少 tierUpdatedAt → 从档案重建"），运维会以为迁移一直没生效。触发面**不止手工改档**：任何被隔离/外部工具改过、或从历史提交恢复出来的档案都符合形状；`player.created`（经 `createArchiveShell`，`server/store/archive.js:308` 有 `tierUpdatedAt: ts`）是正常路径下唯一来源，故正常游戏过程不会触发 —— 这一点必须在文档里写明，否则读者会高估/低估风险。
- **处置建议**（精确到行，已用探针验证）：
  1. `index-file.js:225-231` 改为**只认"缺键"**：`if (!entry || !Object.prototype.hasOwnProperty.call(entry, 'tierUpdatedAt')) return true;`（值 `null` = "已知未知"，不再触发重建）；
  2. **配合**（否则修完仍是"老数据排末尾"的静默错）：在 `server/store/archive.js` 的迁移链里补一条兜底 —— 读档时若 `Number.isInteger(archive.progress.tierUpdatedAt)` 为假，则用 `archive.createdAt`（`Number.isInteger` 时）或 `archive.updatedAt` 盖章并**原子写回**（与 §5.7"读档时按需升级并立即写回"同一机制；`createArchiveShell` 已用 `createdAt` 作为该字段语义，口径一致）。这样"档案缺字段"在 `readArchiveRaw` 阶段就被补齐，索引重建一次即收敛。
  3. 若**不愿**改档案语义（字段缺失要保留"未知"），则必须同时改文档：把 `docs/systems/11:463` 与 D-171⑤ 的"一次性迁移"改为"**索引缺键才重建；档案缺字段者保持 `null` 并排本段位末尾，可能每次开机重建**"，并把它登记为性能项（与 R-5 同处）。
  4. **回归**：`tests/api/api-leaderboard.test.js` 追加 **LB-8**（同 F7-A 用例文件即可）：删掉**档案**字段（而非只删索引字段）→ 重启两次 → 断言"第二次开机**不再**出现 tierUpdatedAt 迁移日志"且 `index.needsTierStamp() === false`（当前 `LB-7` 只删**索引**字段，故漏掉了这条路径）。

### F7-C（P2）段位榜"到达时间"的"缺失=本段位末尾"与 `null` 在响应里的语义未在分册正面写明

- **位置**：`docs/frontend/05-tournament.md:130`（`data.rows[i]` 的 `tierUpdatedAt`）＋ `:176`（T-8 只兜底"显示未知"）＋ 实现 `server/store/index-file.js:161-162`、`:203`
- **主张**：分册把 `tierUpdatedAt` 登记为行字段，但**没有**写明"排序键缺失时排在本段位末尾"这一**排序后果**（只在 `docs/systems/11:783` 与代码注释 `index-file.js:152-153` 有），也没有写明"段位下降/管理端改档会刷新到达时间"（该口径在 `docs/systems/11:783` 与分册 §13 R-6 有）。前端 `format.stamp(null)` 显示"未知"，因此**同一段位内"先到者在前"可能被 `未知` 行打破**而屏幕上看不出原因。

### F7-D（P2）榜人数在会话中途减少时，前端仍按陈旧 `offset/limit` 渲染 ⇒ 空页 + 自相矛盾的"第 2/1 页"

- **位置**：`public/actions.js:1547-1560`（`pageBoard` 只夹 `next < 0`，不比较 `total`）＋ `public/format.js:1793-1803`（`boardHeadText` 用**状态**里的 `offset/limit` 与**响应**的 `total` 现算 `page/pages`）＋ `public/format.js:1823-1835`（行区按同一 `offset` 决定是否渲染）
- **主张**：切榜/翻页把 `offset` 落在 `state.board`，而分页总数只在**响应**里；当 `total` 在两个请求之间缩水（账号被删 / 被封禁 / 搜索范围人数减少），客户端不会回退页号。T-9 只声明"以服务端 `hasMore` 为准、如实显示本页为空"，**没有**规定"榜头页号/页数不得自相矛盾"，于是会出现屏幕文案与数据打架。
- **反例（构造性，纯前端状态即可复现，1 账号即可）**：
  1. 20 人榜 + `limit=20` → 用户点「下一页」→ `state.board.offset = 20`，服务端 `hasMore=false`；此时**其余 19 人被删**（或封禁 + F7-A 已修）→ 响应 `{total:1, offset:20, limit:20, rows:[], hasMore:false}`；
  2. `boardHeadText` = `limit>0 && total>0 ⇒ pages = ceil(1/20) = 1`，`page = floor(20/20)+1 = 2` ⇒ 屏幕显示 **`第 2/1 页 · 共 1 人`**（页号大于页数）；
  3. 行区 `list.length === 0` ⇒ 追加 `（本榜暂无玩家）`，但同一屏的"共 1 人"说明榜里**有人**；「上一页」可用 ⇒ 用户点回 `offset=0` 才自愈。
- **严重度**：**P2**（不是数据错误，但是**用户可见的自相矛盾文案**，且与 §3.2 的"榜头行 + 行区"约定不一致；触发需要"会话中途人数下降"，正常单机走查不易碰到）。
- **处置建议**：在 `loadBoard`（`actions.js:1521-1535`）的成功分支加一条**一次性**夹取：若响应 `data.total > 0` 且本次 `offset >= data.total`，则以 `offset = Math.max(0, Math.floor((data.total - 1) / limit) * limit)` 重发**一次**（`allowBack` 同 F2 的 `loadAccounts` A-4 写法，`actions.js:372-387` 已有同型先例：`count === 0 && offset > 0` 自动回退一页且最多回退一次）；或至少在 `boardHeadText` 里对 `page > pages` 的情形显示"（本页已超出，请点「上一页」）"。**回归**：TB-8 追加"人数缩水后点下一页 → 必须回到含行的页"（当前 TB-8 用 3 个账号、`limit=20`，`hasMore` 恒 `false`，**`hasMore=true` 分支从未执行**）。
