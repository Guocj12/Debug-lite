## 缺口自查（四项按任务要求逐条）

① **顶段位 + wins<7 → 200 不晋升（非 409）的语义**：**确定（成立）**——实现顺序 `!willPromote → 200` 在顶段检查**之前**，因此 mythic+wins=6/0 → 200 `{tier:'mythic', promoted:false, reward:'mythic', wins}`；只有「wins>6 但已是顶段」才 409 already_max（probe1 函数层 + probe2 HTTP 层双实证）。与契约 409 语义（「想晋升但不可」）一致，RK-2h 的 mythic「不再晋升」以 409 表达为 API 层正确映射。

② **tierReward 与 B17 开箱品质上限双实现的漂移**：**存在漂移风险（登记）**——两者语义同源（D-122：段位序号即品质上限）且当前逐档一致（probe1 机器断言：`tierReward(t) === items.rollQuality 池上限`，5 档全等），但为**独立实现**：`tierReward`（ranked.js:156-159，TIERS.indexOf → TIERS[idx]）vs `items.rollQuality`（items.js:46-63，TIERS.slice(0, capIdx+1) 截断池），且三处模块各自维护同一 TIERS 字面量（ranked.js:17/unlock.js:16/items.js:25）。若 TIERS 顺序或封顶语义变更，两处可静默漂移且现有门禁/测试不察觉（无交叉断言）。**建议**：① 指定单一权威——unlock.js 导出 `TIERS`/`tierIndex` 供 ranked/items 复用（低代价）；或 ② 补一致性断言（`tierReward(t) === TIERS[capIdx]` 的交叉测试，probe1 断言可直接移植）。→ P2-3。

③ **promote 缺少 wins 上限（wins=999 → 照样晋升）**：**可接受但建议约束（登记）**——D-123 下 wins 由调用方（客户端）传入，服务端为无状态判定器；契约（T-RK-2/RK-2a..h）语义为「10 场内胜场」，wins=999 属语义外输入但实现仍判定晋升（probe1 实证）。项目内有请求防护先例（box.js `BOX_TIMES_MAX=100`）。**建议**：上限 `wins ≤ 10`（10 场语义上限）或登记契约「wins 由调用方保证 ∈[0,10]」；当前行为不构成安全/一致性缺陷（顶段仍正确封顶，probe1 mythic+999 → 409）。→ P2-2。

④ **CLI 无 promote 子命令**：**合规确认（无需改动）**——interfaces §3 CLI 契约只列 `ranked run`（未列 promote）；T-CLI-1 闭环链（开箱→仓库→装配→loadout→校验 AI→对战→回放）不含排位；interfaces.test.js 机器契约 CLI 清单亦无 promote（grep 实证）。故 CLI 无 promote 子命令与契约一致，HTTP 层已有 api 套件 + probe2 全路径覆盖，验收不依赖 CLI。
